# Mud lab: one switcher, many mud methods, one DS session per build (plan, 2026-10-20)

Goal (user 2026-10-20): get as close to the MudRunner mud feel as we can. It does not have to match one to one. The old
MudSheet (v206, parked) looked best ("how it deformed and flowy it was"). Its blockers were per-frame script cost and
scaling to the whole map. D1 (overlay) and D2 (pressed lift) failed on the DS (results/2026-10-20-mud-two-designs-ds.md):
D1 killed the fps and looked blocky, and D2 was slow and choppy. Why they failed: research/2026-10-20-mud-look.md
(D1 had no soft layer, D2 had no simulation). The one good thing from that round was the numpad 3 switcher (a DbgUI
label plus a log line), so this plan makes it permanent.

Read with: CLAUDE.md, research/2026-10-20-mud-look.md, results/2026-10-20-mud-two-designs-ds.md,
research/2026-10-19-whole-map-sheet-issues.md sec 2-3, research/2026-10-19-mud-sheet-script-cost-research.md,
mud-gotchas.md.

## 0. Hard rules (every mode)
- **The voxel ruts are off limits.** That covers rut ops, the rut field, wear (RUT WEAR v234), look ruts, the patch
  meshes and colliders, and the op format. A mode may READ rut data and draw its own meshes, nothing else. Only the
  pressed-lift rut drawing (D2) is an exception the user allowed, behind its own switch.
- **Client look only, unless the mode says otherwise.** A look mode never writes J2, ops, snapshots or anything the
  DS reads. A mode that changes physics (mode 6) is marked MP-RISK and gets a snap test before any look work.
- **Default off.** Off must behave exactly like today. The local AI checks this by grepping every gate it touched.
- **Tests follow the CLAUDE.md TESTING RULES.** One combined session per build. Workbench is for function and look only,
  never for ms or fps. Numbers come from the DS (or the standalone game), with at least 6 runs per mode.
- **Feature freeze still applies.** Mud-lab work IS the mud lane. Ideas outside the mode list go to the backlog's
  "Parked ideas".

## 1. The lab framework
New file `Scripts/Game/Mud/MUD_MudLab.c`. It owns the switcher. It is ticked from the existing call site
`MUD_WorldGround.c:1086` (today `MUD_MudOverlay.Tick(m_fTime)`, which becomes `MUD_MudLab.Tick(m_fTime)`).
- **Mode registry.** Use a small base class (`MUD_LabMode`: `Name()`, `Presets()`, `Enter(preset)`, `Exit()`,
  `Tick(time)`, `Label()`, `Log10s()`) with one subclass per method. Each subclass lives in its method's file or in a thin
  wrapper. A plain switch over mode ids is fine too if inheritance gets in the way.
- **Surface modes** draw the ground's look, so at most one runs at a time: off -> sheet local presets -> D2 presets ->
  D1 presets (until D1 is archived) -> off. **Add-ons** (spray, wet material, tyre sink, ...) are separate toggles and
  can stack on any surface mode.
- **Keys** (TEST_KIT only). Numpad 3 = next surface step. Left Ctrl + numpad 3 = next add-on combination. Numpad 1-9 are
  all taken already, so do not take another key.
- **Label.** DbgUI top left, as today (`MUD look (numpad 3)`, `step N of M`), plus a line for the add-ons that are on.
  It shows while any mode is on, and for 3 s after switching to off.
- **Log on every switch:** `MUD lab: surface <name> preset <p> | add-ons <list> | (key|new play)`.
- **The same 10 s line for every mode,** so all runs compare in one table:
  `MUD lab 10s: surface <name>/<p> add-ons <list> | fps avg <f> min <f> | MUD ms <f> | mode ms <f> | tiles <n> built <n> kept <n> | <mode extras>`.
  MUD ms comes from the existing frame meter or FrameLog (the same number the 2026-10-20 results used).
- **New play** resets everything to off.
- **Test route:** the existing robot (driver seat, stopped, hold Space 3 s, 2 min reverse circle, RUN_SEC 120) on
  grass. Every mode uses the same route. Add a second truck when a mode claims multi-vehicle support.

## 2. Modes, in build order
Each mode gets a budget (cost while driving one truck, over 'off', DS client) and a kill line.

### Mode 1 - sheet local (surface) - stage 1
The old MudSheet itself, client-only and decoupled: its own stamp, ridges, bow wave, slump, drag and 10 Hz live rebuild
at 0.15 m. This is the only option that has all seven look parts (research/2026-10-20-mud-look.md sec 2).
- **Switching.** `MUD_MudSheet.ENABLED` becomes a runtime `static bool` set by the lab (today it is a `static const`).
  On Exit, every sheet tile entity and all sheet data are freed. On Enter, the sheet starts from fresh state.
- **Couplings off.** In sheet local, every rut file must behave as if the sheet were off:
  - `SYNC` = false. That disables the op tag (MUD_VoxelProbe ~3396), `RUT_SHEET_MS` / `RutUnderSheet` (~1428-1434),
    `MUD_MudSync` (`OnHere`) and the A2 patch lift (`PatchLiftOn`).
  - `ONE_GRID` = false, as it is already.
  - `LAZY_RUT_MESH` = false.
  - `MUD_LookRuts.SHEET_LOOK` = false and `SHEET_SKIP` = false.
  - `MUD_MudZoneEntity.SheetCovers` (MUD_MudZone.c:62) returns false unless the old synced mode is compiled in
    (`ENABLED && SYNC`). This one gate covers the remaining callers: MUD_LookRuts 236 / 368 / 512 / 613 and
    MUD_VoxelProbe 1433 / 3980 / 8445.
  - The local AI lists every reference from a rut file to `MUD_MudSheet.*` or `SheetCovers`, with the gate that keeps
    each one inert.
- **Where it draws (sparse).** No zone pre-build and no whole-map RADIUS. `SPARSE` is currently false with a stale
  'whole-map test' note; local mode does not use it.
  - Tiles exist only around the wheels of vehicles near the camera.
  - The **BORN** rule is a preset: (a) a tile is born when a stamp touches it, or (b) a tile is born ahead, within 1 tile
    of a wheel, so the raised layer is already there when the tyre arrives.
  - A tile that never got a stamp is dropped after DROP_S (start 5 s) once no wheel is near it.
  - Stamped tiles are kept, with a cap (start 1500 tiles, about 100 MB at the measured ~60-75 KB per tile). The tiles
    farthest from the camera are dropped first; the voxel rut stays there.
- **Edge fade.** A tile side with no sheet tile next to it is an OPEN side and fades into the ground over EDGE (1 m).
  Today `HasTile` means "covered ground", which is wrong for sparse tiles.
- **Several vehicles.** The live window (FOLLOW) follows the nearest vehicle only today. In local mode:
  - every vehicle within STAMP_R of the camera (start 80 m) stamps into tile data;
  - the nearest LIVE_N (start 2) get the 10 Hz live rebuild;
  - the others rebuild at the stored pace (0.25-0.5 s).
- **Holes.** Crater and dig tiles are rebuilt in the blast frame (do not wait in `UploadPick`). The `DigNow` stored path
  (MUD_MudSheet.c ~3446) also rebuilds its taper neighbours (`QueueTaperNeighbours`).
- **Base height.** Keep the sheet's own ground read as v206 had it. Check by eye that the tyre sits in the sheet groove
  over the felt voxel rut (no floating, no tyre buried in mud).
- **Presets:** BORN a / b x THICK 0.15 / 0.08 (4 presets).
- **Budget:** at most ~3 ms/frame over 'off' with one truck. Measured references: 'sheet' 1.3-1.8 ms in the old zone,
  plus slump at an estimated 0.3-0.5 ms.
- **Kill** if it is over budget after mode 4's perf work, or if it does not look like the old sheet.
- **Known limits:**
  - every client sees its own stamps (close but not identical);
  - a late joiner, or someone far away, sees only the voxel ruts. A fallback is later work; D1's fallback code can be
    copied.
  - grass rides on the raised band (the old sheet had this too; check by eye).

### Mode 2 - wheel mud spray (add-on) - stage 1
Mud thrown by the wheels, client-only, script-driven so the lab can switch it.
- Emit a vanilla wheel dirt or mud particle at the wheel contact while the wheel is in mud: on sheet-local tiles, or on
  rut dirt (`FIELD_SOIL_D` or the rut mud gamemat).
- The rate follows wheel speed and slip. Cap the particles per wheel, and emit only within SPRAY_R of the camera
  (start 60 m).
- Research note: vanilla land gamemats have no wheel mud effect, only `water_base.gamemat`. Our rut gamemat
  `Common/Materials/Game/mud_rut.gamemat` inherits `soil.gamemat`. A data route (a ParticleEffectInfo copied from
  water_base into mud_rut) is cheaper but cannot be switched by the lab. Try it only after the user has picked a look.
- **Muddy vehicles:** check by eye only. The engine's dirt counters already fill on our ground. Note in the session
  whether the truck gets visibly muddy.
- **Budget:** under 0.3 ms/frame for 1 truck. **Kill** if it looks like dust, or if it is over budget.

### Mode 3 - wet mud material (add-on) - stage 2
A dark, wet mud emat on the sheet's dirt section (and on D2's floor, if D2 is kept). It uses WaterAccumulation and a
parallax HeightMap if the vanilla mud materials have them. The only cost is the material itself. Compare by eye against
today's emat.
- **Kill** if it is shinier than vanilla wet ground, or if it has visible tiling.

### Mode 4 - sheet performance (applies to mode 1) - stage 2
Measure the levers one at a time with 1, 2 and 4 trucks:
- Part A switches that are built but never run on the DS: A1 `SLUMP_ONE` (sync-only, it no-ops in local mode), A2
  `DRAG_STRIP`, A5 stored render gate (`STORED_GATE_NEAR`);
- the natives purge (research 2026-10-19 sec 8);
- 1.5 m live tiles;
- the `IsRendered` gate on stored tiles;
- cheaper mud for far trucks (stamps only, slump off past LIVE_N).
Keep a lever if it saves at least 0.2 ms/frame with no visible change.

### Mode 5 - tyre sink visual (add-on) - stage 3
Use `WheelSetRadiusState` (the probe was never run) to draw the wheel lower in deep sheet mud. First a one-wheel
probe: does it change only the look, or the contact as well? If it changes contact, it becomes MP-RISK like mode 6.

### Mode 6 - mud drag / bogging (MP-RISK) - stage 3
Rolling resistance from mud depth, so trucks slow down and can get stuck. It has worked in SP only. The snap test comes
first: a DS plus 2 clients, the robot route at 3 drag levels, at least 6 runs each. Compare the 'MUD corr ... mine 1'
snap counts against off. The look work starts only if the snaps do not rise.

### Mode 7 - splash decals and debris clods (add-on) - stage 3
- `World.CreateDecal` mud splats beside deep ruts. It returns null even when it works, so judge by eye.
- Small clods from an `SCR_DebrisSmallEntity` pool, capped.
- **Budget:** under 0.3 ms/frame.

### D1 / D2
They stay in the cycle until the user archives them, after the stage 1 session if sheet local wins. Archive means
`mud_backups/archive/<name>-<date>/` with a README of call sites; never delete.

## 4. DS session template (stage 1)
DS + PeerPlugin1, a fresh truck after start, robot reverse circle on grass, at least 6 runs per row.
1. off: baseline while DRIVING. The 2026-10-20 'off' rows were standing, so they are not a baseline.
2. Sheet local, each preset: MUD ms, mode ms, 'sh wheels' / 'sh upload' / 'sh stored' / slump ms, tiles.
   By eye: does it deform and flow like the old sheet; do tile edges fade (no step); BORN a vs b pop-in; grass on the
   band; is the felt rut still felt; does the tyre sit in the groove.
3. D2 preset 4: the same numbers.
4. Spray on top of sheet local, then on top of off: by eye, plus mode ms. Is the truck getting muddy?
5. Crater + short trench in a sheet area: are the holes clean, any late tiles?
6. A second truck about 40 m away: does it leave mud (stored pace)? MUD ms with 2 trucks.
7. A late-joining client: what does it see? Expected: voxel ruts only.

Results go to `results/2026-10-2x-mud-lab-stage1-ds.md`, with one table using the 10 s line columns.

## 5. Feasibility (the honest version)
- **Feasible:** the old sheet's look around the action. That is wherever wheels go near the camera, with tiles kept
  along tracks.
- **Whole map:** only in the sparse sense, which is also what MudRunner does (dense mud only where it exists, simulation
  near the player). A sheet over all ~5.6 km² of holed ground cannot be built: about 622,600 tiles, 37-47 GB, and
  6-30 min of builds.
- **Hard limits:**
  - script-only mesh builds, so the cost grows with busy trucks (~1-2 ms/frame per live truck before the mode 4 work);
  - no shaders, no vertex colours, one UV set, one mesh LOD;
  - MP physics feel (drag, stuck) risks snaps, so it is tested before it is built out;
  - every client draws its own mud. That is close, but not identical between clients.
