# Audit: op / rut / per-frame script cost (2026-10-18)

Read-only audit of Scripts/Game/Mud, excluding MUD_WorldGround.c, MUD_FinePatch.c and MUD_BandMesher.c (another audit
covers those). No code was changed. Line numbers are from the working tree on 2026-10-18, after the RUT_RAMP edit.

## Summary (plain)

1. One rut op costs about 12.8 ms on the DS and about 9.3 ms on a client (measured, means of printed ops). Most of that
   is RelaxFloor (6.4 ms) and GrowRidges (2.8 ms), and both spend most of their time in FloorBase per sample.
2. FloorBase asks WorldGround.Heights for the undug height. Heights also works out the dug height (floor, locks,
   ridges) and then throws it away. A cheaper "undug only" path gives the same numbers and is the biggest single win.
3. On the DS every op Prints 2-3 lines while TEST_KIT is true. One Print on the DS costs about 1.8 ms (measured), so this
   adds about 2-4 ms per op. The hash lines are needed only for J2 runs, so they should get their own switch.
4. Per op, the code builds fresh maps and repeats the same lookups (FloorDiv, ColKey, map Get) for each sample. Small
   reusable grids and per-op caches would cut this further while keeping the floor identical on every machine.
5. Per frame: every vehicle, parked ones included, gets a rut track, a FindComponent call three times and a JoltProbe
   ground probe, and MUD_Prof writes a 49-column CSV row. These are small but always on. **RampChains does not compile
   (prv/nxt declared, prev/next used).**

## Details

### 0. RampChains compile error
MUD_VoxelProbe.c:4806-4807 declares `array<int> prv` and `nxt`, but 4813-4814 call `prev.Insert` / `next.Insert` and
4827-4828 set `prev[s] = j` / `next[j] = s`, while 4825 reads `nxt[j]`. These are undeclared identifiers, so the file
will not compile. Fix: use one name pair throughout. RUT_RAMP is true (268), so this path runs.

RUT_RAMP cost (inference): RampChains is an O(n^2) backward search with an early break, at most 40 segments
(RUT_MAX_SEGS), and about 6 compares per segment at 6 wheels. That is negligible. RampW (4860) is a few flops per sample.
In the segment loop, `Math.Sqrt(len2)` is recomputed per sample but depends only on the segment, so hoist it. RampBehind
(4868) runs a box loop of about ((1.0 + 0.6) / 0.25)^2, about 40 samples per chain head, each with a Sqrt plus map ops:
about 0.1-0.3 ms per op. The m_mRampW member map is Cleared and refilled per op and read in the write loop; it can move
into the dense grid of #4.

### 1. Undug-only height (biggest win)
Path now: FloorBase (4930) -> ColAt -> Kept -> Hard -> `MUD_WorldGroundEntity.UndugY` (4958) -> WorldGround UndugY
(3537) -> `Heights(x, z, dug, y)` (4796). For dug, Heights reads 4 GetH (each a map Get), FieldFloorAt (4 floor
lookups) and 4 LockAt, and with ridges near zero it also reads FieldTopAt (4 more samples + 4 LockAt). Only `undug`
goes back to FloorBase, and undug comes from BaseAt (2856) plus a GetSurfaceY fallback.
Change: a static `BaseY(x, z, out y)` that runs only the undug part. FloorBase runs once per written sample, per new
relax sample and per ridge key, so this applies to write (1.47 ms), relax (6.43 ms) and ridge (2.78 ms) on the DS.
Also used by: LookRuts LookBase (5414) in Cut, PinLift (MUD_PinLift.c:70, about 600 ms at load) and VoxelProbe 3058,
4209 and 6592.
Risk: none if BaseY is the same expression Heights uses for undug. Check with a J2 run (hashes equal) and one DS run
with the op-time lines.

### 2. Prints per op on the DS
- 6489 DispOpDone: `MUD disp hash` for every rut op while DispOn(DSW_HASH), which is true whenever TEST_KIT. It falls in
  'post', and DS post is 1.86 ms vs client post 0.10 ms (measured, 129 vs 92 printed ops), so it costs about 1.8 ms per
  op on the DS.
- 4001: `MUD field hash` per op when TEST_KIT.
- 3808 Submit: `MUD op time` when all >= OP_SLOW_MS (8). The DS mean is 12.8 ms, so nearly every op prints, and that
  Print falls outside the timed 'all'.
- MUD_JoltProbe.c:213 `MUD corr trace` (128 lines on the DS) for 6 frames after each correction, plus RutNear (60) at
  236, which loops the 4096-entry ring times the wheels.

Change: a `HASH_LOG` const for the two hash lines (on only for J2 / compare_op_hashes runs). OP_SLOW_MS 20, or a
max/mean in the 10 s Stats line. JoltProbe only under TEST_KIT, and TEST_KIT false for perf runs (user call).

### 3. Per-op caches around FloorBase
- Kept (6101) / Hard (6077) depend only on the 0.5 m column (cgi, cgk = round(fi * 0.5)), so about 4 floor samples
  share each answer. Cache them per op in a small grid.
- ColAt / ColRound (5182, 4 ColAt) return null on plain ground. One check per op ("does any voxel column overlap the op
  box?") lets the whole op skip them.
- FloorSample (5148) / RidgeSample: 2 FloorDiv + ColKey + map Get per call. Keep the last tile and its key, and reuse
  them while the next sample is in the same tile (16x16 samples per tile).
- FloorBase on plain ground does not depend on nearY, so write, relax and ridge can share one result per sample.

Risk: low, provided the op does not change what is cached (it changes only the rut floor, not columns or holes).

### 4. Dense grids instead of maps
Each op allocates:
- CarveFloor: the maps best, atY and bestSeg, plus the segCut and wrote arrays.
- RelaxFloor: the map `at`, 7 arrays, the ringSeen set, ring and nbOff.
- GrowRidges: the maps rise and atY.

Relax pass 1 makes 25 neighbour `at.Contains` calls per written sample, then 4 iterations x ring x 4 neighbours x
(Contains + Get). The op box is about 26 x 30 samples (mean 794, max 1050, measured). A reusable float array of
(w+4) x (h+4) with a "set" stamp array would replace every map call with an index.

Key = rk * RUT_KEY_W + ri, so row-major iteration of the grid gives the same order as the sorted keys RelaxFloor and
GrowRidges use now. The disp hash is additive mod DISP_HASH_M (385), so its order does not matter anyway. LookRuts Cut
(323) can use the same pattern.

Risk: medium, mainly from rewriting loops. Prove it with compare_op_hashes on a J2 run before and after.

### 5. Client op spikes
Drain (1491) stops after DRAIN_MS 4, but the check runs between ops, and one op is 9-12 ms on the client (measured op
time; worst vox frames 11-13 ms). After #1-#4 an op may be about 3-5 ms (inference), which mostly removes the problem.
If not, split CarveFloor into phases (segments / write / relax / ridges) that resume next frame, keeping op order.
[SUGGESTION] Sending the result (floor deltas, about 1-1.5 KB per op, inference) instead of the op would remove client
carve entirely, but it breaks the current J2 model; keep it as a parked idea.

### 6. Vehicles: parked ones and repeated FindComponent
RutFlush (1159) calls Track(veh) (1384), which searches linearly and creates a track when none exists. WorldGround Wheels
calls RutFlush for every vehicle, parked ones too, so s_aTracks holds every vehicle and each frame costs O(V^2)
compares. Use a lookup that does not create for parked vehicles, and a map keyed by entity. MUD_Wheels, JoltProbe and
LookRuts each call FindComponent for the wheeled simulation every frame per vehicle; a per-frame sim cache in MUD_Wheels
removes two of the three.

### 7. Look ruts (client)
Counters per 10 s (client, measured, counts only): cuts 176, samples 3238-3836, look meshes 139-161 taking 673-811 ms,
replaced 160-322, expired 480-648, Cut/Sweep own time 101-114 ms.
- Cut runs every EVERY 0.05 s (73) and goes through LookBase -> FloorBase, so #1 applies.
- REPLACE 3 s / REPLACE_MIN 0.03 m (80, 84) drive the replaced rebuilds. Raising REPLACE_MIN to about 0.05 m, or EVERY
  to 0.1 s, trades pop-in for fewer mesh builds (user call: the ruts were made faster on purpose).
- Sweep (513) scans all tiles x 256 samples every 0.5 s; keep a dirty-tile list instead.
- Tick 148-151 calls 4 TEMP probes first (MUD_DecalProbe, MUD_RoadHideProbe, MUD_GrassCutProbe, MUD_TrackStamps), each
  with its own switch. The TEMP delay meters (s_aMark / s_aWait / NoteBuilt / NoteDelay) also run.

### 9-10. Minor
- Issue (3366): Decode(Encode(src)) + Prepare, then Encode + Decode + Prepare again, then Submit Prepares a third time.
  PrepareRut (3657) does Split ";" plus up to 40 x Split "," with 6 IsInt each. Skip the second round trip outside
  TEST_KIT.
- SubmitBody 4071-4098 builds `label` / `what` with string.Format every op although OP_LOG is false.
- m_aOps.Insert (4069) keeps every op forever (memory, and JipSendTick reads it).
- RutFlush has a dead RUT_BEHIND Print (RUT_BEHIND is false).
- Parked mud sheet / sync: MudSheet.Tick returns at once (ENABLED false), and MudSync.Flush (3843, 1515, 1813) is a
  no-op per op. Cost is near zero; no change needed.
- Graves (per frame) returns at once when empty; SnapGate, JipSendTick and AskJip return early. All fine.
