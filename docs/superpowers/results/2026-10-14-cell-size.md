Measured 2026-10-14 with Tools/dc_vertex_proto.py, `DC_CELL=0.25` vs `DC_CELL=0.5`, rut shapes only, same game op
formulas (CarveRut 6 passes x 0.08 m to cap 0.33 m, RUT_R 0.5), same 12 x 12 m grid and measured region as B1.
Methods: mean (today's CellPos) and dc_cd (B1's best). Logs / tables: docs/superpowers/results/2026-10-14-cell-size/.

## Cost in game (estimate, INFERENCE from the Python counts - not measured in game)

- Per 4 m brick: samples 8x (Gather, the Polygonize loop), surface cells / verts / tris ~4x (CellPos, mesh,
  CreateTriMesh). Python whole build 7.4-7.6x because its vertex loop also walks empty cells; the game's CellPos
  only runs on surface cells, so expect ~4-8x per brick.
- Today: client build 34.7 ms per second of driving (v037 run 10-14 00:10; v035 was 20); the Step A JIP join
  built 839 ops in 1721 ms. At 0.25 everywhere: ~140-280 ms/s while driving and ~7-14 s of build on join. Far over
  budget.
- "Only rut bricks at 0.25" means two resolutions side by side: their seams don't match (cracks) without transition
  cells - the plan's "not taken" item. So a rut-only fine grid is a big design change, not a switch.
- MAX_V 8000 per brick: a busy brick at 4x verts can get near it.
- The 8^3 brick size is written into the code as numbers (10x10x10 sample grid = 100 / 10, 9^3 cells = 81 / 9 / 729,
  cache 11664): a grep for those numbers hits 80 lines of MUD_VoxelProbe.c (not every hit is a grid size). A SUB 16
  probe is a real refactor, not a constant change.

## What it means

- 0.25 m cells are what makes ruts sharp (B1 proved the 0.5 m vertex can't), and they do it well.
- But the cost (4-8x build) rules out "everything at 0.25". Options:
  1. A game probe anyway (refactor the brick size constants, one SP drive, read build ms/s) to replace the estimate.
  2. Rut-only fine bricks with transition seams - big, risky.
  3. Leave 0.5 and change the rut PROFILE so the 0.5 grid can hold it (today's CarveRut profile drops from half
     depth to 0 at RUT_R: a step no 0.5 m grid stores). A wider, smooth-edged profile would draw as designed.
     Cheap, but ruts stay soft-edged.

## Game probe, SP (Exp 192624, WB console logs_2026-10-14_18-07-47)

Coarse control (0.5 m, after the size refactor), robot drive 19:18:02-19:19:29. Sums over all 255 'MUD voxel
probe: live' lines (the first at 19:18:22, the last at 19:19:29: 67.4 s):

| setting | ops | builds | builds/s | build ms | build ms/s | verts | latency mean / median / max ms | worst frame max / mean ms | worst brick ms | go-live max ms | end columns / bricks |
|---|---|---|---|---|---|---|---|---|---|---|---|
| 0.5 m | 499 | 4646 | 68.9 | 4331 | 64.3 | 193527 | 52 / 52 / 88 | 11 / 10.0 | 3 | 3 | 99 / 159 |
| 0.25 m | 585 | 2790 | 31.1 | 32369 | 361.0 | 665807 | 312 / 213 / 13792 | 29 / 21.7 | 20 | 6 | 107 / 107 |

- No script errors from the refactor. 64.3 ms/s is SP (one machine cuts the ruts and builds the bricks), so it is
  not comparable with the 34.7 ms/s MP client figure.
- The first fine try did not compile (the Enforce array and class size limits, see mud-gotchas). Fixed (MAX_V 10000).
- Fine run 19:23:25-19:25:13 (218 live lines, 89.7 s): 0 overflow lines, most verts in one brick 561 (MAX_V 10000 is
  plenty). Per build 238.6 verts vs 41.7 (5.7x); build ms/s 361.0 vs 64.3 (5.6x). Builds/s fell to 31.1 (URGENT_MS
  budget unchanged), so changes waited: latency mean 312 ms vs 52, worst 13.8 s (19:24:08, seq 15, 104 ops in one
  batch). Worst frame per batch mean 21.7 ms vs 10.0.
- 'Slow brick' lines (>= 16 ms, 688 of 2790 builds): mean poly 9.2 ms, collider 7.3 ms, mesh 0.1 ms. Poly cost
  barely depends on verts (3 bricks under 60 verts: 10.0 ms; 582 over 300 verts: 9.3 ms) - it is the fixed scan of
  the 16^3 samples + 18^3 gather. Collider ~7 ms vs ~1.45 at 0.5 m.
- Verdict: 0.25 m everywhere is ~5.6x the build cost and visibly late (13.8 s worst). Not usable as is. Cheaper
  routes: fine bricks only where a rut is cut, and/or polygonize only the samples near the surface.
